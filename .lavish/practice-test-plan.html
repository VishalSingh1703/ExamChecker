Practice Test: chapter PDF to graded report

Context

Why this exists

ExamChecker today is a teacher-grades-a-student tool. The teacher authors an answer key in Setup, uploads a student's answer sheet in Grade, and gets a report. There is no path for someone to practise against their own study material.

This feature adds a self-practice loop. The intended outcome is that grading, scoring, the report, printing, and cloud sync are the existing engine, unchanged — only the front half (PDF → questions with answers, the blueprint editor, and the timer) is genuinely new.

Four decisions confirmed up front

Marks config
Blueprint rows. Repeatable [N] questions × [M] marks with live totals.
Reports
Stored separately. Practice attempts get their own localStorage key and their own section in History — never mixed with graded exams.
Grading strictness
New "Firm" mode, exactly halfway between Medium and Strict. The practice default.
Saving a paper
Question Bank chapter via the existing saveChapter(). No new table, no migration.
PDF pipeline
Two-stage, cached text. Transcribe once; generate from the cache. Regenerating costs one cheap call.
Tab placement
Header tool row, immediately left of Upload Questions — not in the main Setup/Grade/Report row.
Findings

Three things in the source that shape the design

Each was verified directly against the code, and each one changes what gets built.

Critical

Hallucinated keywords would silently halve every score

src/services/ai/grading.ts:31 — "If required keywords are listed and ANY are absent, cap the final score at 0.5."

If the generator emits a keyword that isn't even in its own expectedAnswer, every student answer for that question is capped at 50%. Generated keywords must be post-filtered to verbatim substrings of the model answer. This is the single highest-risk detail in the feature.

Budget

The 25-question cap is arithmetic, not an arbitrary limit

gradeExtractedText runs at maxOutputTokens: 1024 (grading.ts:148), and that budget is shared with the Grade tab's re-evaluate button. At roughly 20 output tokens per score entry, it covers about 40 questions safely. Hence PRACTICE_MAX_QUESTIONS = 25 — and it isn't raisable without touching a budget grading depends on.

Recommendation

Stay prompt-only for JSON — do not widen GeminiConfig

GeminiConfig (client.ts:16-19) exposes only temperature and maxOutputTokens — no responseMimeType. JSON is coaxed by prompt and rescued by extractJson. client.ts is shared by grading, authoring and OCR, so a silent 400 from the pinned model would break all three at once. The two-stage design already removes most of the risk, because stage 1 returns prose, not JSON.

Structural

An in-progress test cannot live in the view's state

PracticeView mounts behind a tab conditional in App.tsx:123-130, so component-local state dies on every tab switch. The attempt needs a provider above that conditional.

Services

The two AI calls

Both live in a new src/services/ai/practice.ts, routed through the existing callGemini.

  question: string; expectedAnswer: string; marks: number; keywords: string[]
}

export function blueprintTotals(rows: BlueprintRow[]): { questions: number; marks: number };

export async function extractChapterText(
  file: File, apiKey: string, signal?: AbortSignal,
): Promise<string>;

export async function generatePracticePaper(
  input: { chapterText: string; blueprint: BlueprintRow[];
           examClass: string; subject: string; chapter: string },
  apiKey: string, signal?: AbortSignal,

Stage 1 — extractChapterText

For PDFs, use the hardcoded mime exactly as authoring.ts:134 — { inlineData: { mimeType: 'application/pdf', data: await fileToBase64(file) } } — and not filePart, because mobile pickers routinely hand back file.type === ''. Text files go through file.text(); images through filePart.

The prompt asks for the complete chapter as continuous plain text: preserve headings, definitions, formulas, lists and worked examples; omit page numbers and running headers; do not summarise. Config { temperature: 0, maxOutputTokens: 8192 }, signal as the fourth argument, result capped at 60k chars. No JSON parsing at all — this stage cannot fail on malformed output.

Stage 2 — generatePracticePaper

The reliability trick is slot expansion. Small models drift on multiplicative counts ("5 questions of 2 marks") but are reliable against an enumerated table: 

SLOTS — produce exactly one object per slot, in this exact order:
 1. 2 marks
 2. 2 marks
 3. 2 marks
 4. 5 marks
 ...
 9. 10 marks
Total: 9 questions, 45 marks.

The body reuses the depth-scaling bands verbatim from generateModelAnswer (authoring.ts:23-26) so practice answers match bank answers in style; requires every question be answerable solely from the chapter text; and forbids repeated or rephrased questions. The keyword rule is stated explicitly: 2–4 short technical terms that must appear verbatim, character-for-character, inside your own expectedAnswer; return an empty array if you cannot find such terms.

Config temperature: 0.4 — variety matters here, since Regenerate must produce a different paper — and maxOutputTokens: Math.min(8192, 700 + totalMarks * 60).

Parsing and hardening, in order

  1. JSON.parse(raw), falling through to JSON.parse(extractJson(raw, 'array')) — the two proven tiers from parseStructuredQuestions. The line-based third tier is meaningless here, so it's omitted.
  2. Per-item string coercion; drop anything with an empty question or answer.
  3. Overwrite marks positionally from the slot list. Never trust the model's own marks — this makes blueprint totals arithmetically guaranteed.
  4. Filter keywords to expectedAnswer.toLowerCase().includes(k.toLowerCase()). This is the guard for the critical finding above.
  5. Throw a Regenerate-able error if fewer items than slots; truncate if more.
Pipeline

Blueprint to questions

BlueprintRow[] → normalise (merge same-marks rows, drop count 0)
               → expandSlots(): number[]      e.g. [2,2,2,2,2,5,5,5,10,10]
               → ONE callGemini (slot table + cached chapterText)
               → GeneratedQuestion[]  (marks re-stamped positionally)
               → Question[] { id: i + 1, question, expectedAnswer, marks, keywords }

id: i + 1 matches ExamSetup.tsx:216, so the practice Question[] is byte-compatible with SegmentGradeInput, ReGradeInput, QuestionResult.questionId, printReport and RecordDetail — zero adapters.

Validation before Generate

  • Every row count ≥ 1; marks drawn from PRACTICE_MARK_OPTIONS (all ≤ MAX_QUESTION_MARKS).
  • Hard caps: 25 questions, 150 total marks.
  • Soft warning when questions > chapterText.length / 800 — "this chapter may be too short for N distinct questions".

Persistence and refresh survival

  • Write to storageKeys.practice(userId), versioned, debounced 800 ms — typing into 25 textareas must not thrash localStorage — flushed immediately on phase transitions and visibilitychange → hidden.
  • Read in the useReducer lazy initialiser; anything not the current version falls back to initialState.
  • Transient-phase demotion on rehydrate, because an in-flight fetch can't survive a reload: extracting → source, generating → blueprint, grading → testing with an interrupted-submission message.
  • Survives refresh: questions, model answers, typed answers, deadline, attempt id, mode. Does not: uploaded photos, since File isn't serialisable — the photo tab carries a permanent warning saying so.
  • Non-serialisable state — the source File, SheetPage[], object URLs — stays in refs inside the step components, never in the reducer.
Timer

Deadline timestamp, not tick counting

Recomputing from Date.now() on every tick means a throttled background tab that fires once a minute still shows the correct remaining time — decrementing a counter would not. 

export function useCountdown(deadlineAt: number | null, onExpire: () => void): number {
  const [remaining, setRemaining] = useState(() => deadlineAt ? Math.max(0, deadlineAt - Date.now()) : 0);
  const onExpireRef = useRef(onExpire);   // avoid stale closures
  const firedRef = useRef(false);
  useEffect(() => { onExpireRef.current = onExpire; });
  useEffect(() => {
    if (deadlineAt === null) return;
    firedRef.current = false;
    const tick = () => {
      const left = Math.max(0, deadlineAt - Date.now());
      setRemaining(left);
      if (left === 0 && !firedRef.current) { firedRef.current = true; onExpireRef.current(); }
    };
    tick();                                 // immediate — handles already-expired rehydrate
    const id = setInterval(tick, 250);
    return () => clearInterval(id);
  }, [deadlineAt]);
  return remaining;
}
  • Auto-submit calls the same handleSubmit() as the button. firedRef guarantees once, and a phase !== 'testing' guard covers a click landing in the same 250 ms window.
  • Rehydrate is correct by construction — tick() runs synchronously on mount and fires immediately if already past the deadline.
  • Abandoned attempts: if phase === 'testing' and the deadline passed over 24 hours ago, do not auto-submit — clear the deadline and offer "Submit what you have / Discard".
  • A beforeunload guard while testing, so an accidental refresh prompts first.
  • Sticky MM:SS bar — amber under 5 minutes, red under 1 — plus a progress bar. No Date.now() in render outside the hook.

Strictness

A new "Firm" mode for practice

Practice should be a little harder than a real exam, so a student who scores well here is comfortable in the actual paper. Medium is too forgiving for that and Strict is punishing — Strict awards zero at 50% similarity, which reads as broken to someone practising alone. So Firm sits exactly halfway between them. 

// src/utils/scoring.ts — one new branch
Easy    ratio = max(0, 1 − (2/3)(1−s))    // −10% marks per −15% similarity
Medium  ratio = s                          // exact linear
Firm    ratio = max(0, 1.5s − 0.5)         // ← NEW: the midpoint of medium and strict
Strict  ratio = max(0, 2s − 1)             // −10% marks per −5% similarity

Firm is the arithmetic mean of Medium and Strict at every point: (s + (2s−1)) / 2 = 1.5s − 0.5. A perfect answer still earns full marks; the penalty for drifting is 1.5× Medium's instead of 2×; zero arrives at 33% similarity rather than Strict's 50%.

Marks after the existing round-to-nearest-0.5 step. Firm is consistently one band below Medium without collapsing to zero as early as Strict.

What this costs

  • CheckingMode in types/index.ts:50 widens to 'easy' | 'medium' | 'strict' | 'firm'. Widening a union is backward-compatible for reads — every saved HistoryRecord already holds one of the original three, so no migration.
  • MODE_LABELS in constants.ts:12-16 is typed Record<CheckingMode, …>, so TypeScript forces the new entry — the compiler catches the omission rather than a runtime undefined reaching a Badge className.
  • One branch in calculateMarksByMode. The status derivation and the 0.5-rounding are untouched.
  • CHECKING_MODES (the array driving Setup's teacher-facing selector) stays at three. Firm is offered through the practice screen's own selector, so the Grade tab's behaviour doesn't shift under teachers who didn't ask for it. Promoting it to Setup later is a one-element change.
Report

Kept apart from graded exams

Practice attempts must never dilute a teacher's real records. Separation happens at three levels — storage, display, and stats — so a practice run cannot leak into the archive, the analytics tree, or the usage meter.

LayerGraded examsPractice attempts
localStorage exam-history-<uid> practice-history-<uid>
Supabase reports table, kind absent same reports table, kind: 'practice'
History tab Archive tree — year → class → section → subject Practice section — flat, newest first
Analytics Included Excluded entirely

A separate localStorage key is the important part: the two lists never share an array, so no filter bug can surface a practice run inside the archive. In the cloud they share the reports table because a second table means a migration and new RLS policies for zero behavioural gain — the kind field segregates the rows, and every loader filters on it at the point of read.

Risks

What could go wrong, and the guard

Critical Hallucinated keywords cap every score at 0.5
Post-filter keywords to verbatim substrings of expectedAnswer. Top priority, and explicitly checked in phase 03.
Limits Large PDFs
Base64 inflates by 4/3 and Gemini's inline limit is around 20 MB. Reject over 15 MB up front; the spinner notes that large files can take a minute.
Limits Silent extraction truncation
8192 tokens is roughly 12–15 dense pages, and callGemini doesn't surface finishReason. Show the extracted character count; warn above 28k chars with "upload one chapter at a time".
Limits The 1024-token grading budget
25 questions costs about 500 tokens. Don't raise the question cap without raising a budget the Grade tab shares.
Handled Malformed generation JSON
Two-tier parse, per-item coercion, count validation, and a prominent Regenerate that costs zero extraction. Stage 1 is prose, so it can't fail this way at all.
Handled Model returns the wrong marks
Never read the model's marks — stamp positionally from slots, so blueprint totals are arithmetically guaranteed.
Handled Blueprint exceeds what the chapter supports
Hard caps at 25 and 150, a soft warning at chapterText.length / 800, and a prompt that forbids repetition.
Handled Refresh mid-test
Debounced persist, a visibilitychange flush, and a beforeunload guard. Photos are the known casualty, warned in-UI.
Handled Abandoned attempts
A 24-hour staleness check offers "Submit what you have / Discard" rather than silently submitting a days-old attempt.
Handled RESET_SESSION destroying an attempt
Practice never writes ExamContext; it only reads the API key.
Handled Double-submit and duplicate rows
firedRef plus a phase guard on submit; attemptId serves as both record id and session id, with savedSessions guarding local and ignoreDuplicates guarding remote.
Handled Practice polluting teacher data
A genuinely separate localStorage key means the two lists never share an array, so no filter bug can surface a practice run in the archive. Analytics additionally filters kind on the cloud merge, and incrementUserStats is skipped.
Handled Widening CheckingMode breaking saved records
Adding a union member only widens what is accepted — every stored record already holds easy, medium or strict and still parses. MODE_LABELS is a Record<CheckingMode, …>, so the compiler refuses to build until the firm entry exists, turning a would-be runtime undefined into a build error.
