SECTION 1 — MEMORY LEAKS (you are leaking memory everywhere)
--------------------------------------------------------------------------------

[HIGH] GradingView.tsx — useEffect cleanup closes over empty pages array
  Lines 51-54:
    useEffect(() => {
      return () => { pages.forEach(p => URL.revokeObjectURL(p.url)); };
      // eslint-disable-next-line react-hooks/exhaustive-deps
    }, []);

  The dep array is empty, so the cleanup function captures the initial value of
  `pages`, which is []. When the component unmounts, it iterates over nothing.
  Every object URL added after mount is permanently leaked. The eslint-disable
  comment is hiding the bug, not suppressing a false positive.

  Fix: either keep a ref to the latest pages, or add pages to the dep array and
  accept that cleanup runs on every change (fine for cleanup purposes).

[HIGH] QuestionGrader.tsx — imageUrl leaked on unmount
  Line 51: setImageUrl(URL.createObjectURL(file))
  Line 49: revoke only on NEW file selection.
  There is no useEffect cleanup. If the component unmounts (user switches tabs,
  session resets) with an image loaded, that object URL is gone forever.

[HIGH] QuestionPaperBuilder.tsx — photoPreview URL leaked entirely
  Line 269-270:
    const url = URL.createObjectURL(file);
    setPhotoPreview(url);

  No revoke on unmount, no revoke when a second file is selected (handlePhotoSelect
  overwrites photoPreview state without revoking the old URL first).
  Every image the user picks in this component leaks memory permanently.

[HIGH] Tesseract worker never terminated
  src/services/ocr.ts exports terminateOCRWorker() at line 414.
  It is called NOWHERE in the codebase. The Tesseract worker thread (~15-20MB)
  lives forever for the entire browser session. This is especially bad on mobile.

[HIGH] GradingView.tsx — videoFile URL not revoked on unmount
  Line 116: setVideoFile({ file: f, url: URL.createObjectURL(f) })
  clearVideo() at line 122 does revoke it, but there is no useEffect cleanup.

SECTION 3 — SECURITY
--------------------------------------------------------------------------------

[CRITICAL] Gemini API key stored in plain text localStorage
  ExamContext.tsx line 22:
    geminiApiKey: ... ?? localStorage.getItem('gemini-api-key') ?? ''

  API keys in localStorage are readable by any JavaScript on the page, including
  browser extensions, injected scripts, and XSS payloads. This is a well-known
  bad practice. The key should be session-only (no persistence) or the app should
  rely entirely on the env variable injected at build time.

  If you insist on user-entered keys, at minimum don't persist them to localStorage.
  Store in memory only (React state/context). The user types it once per session.

SECTION 4 — INCONSISTENCY THAT WILL CAUSE WRONG SCORES
--------------------------------------------------------------------------------

[HIGH] similarity.ts reads Gemini key from ENV, ignores the user-entered key
  Line 144: const geminiKey = (import.meta.env.VITE_GEMINI_API_KEY as string | undefined) ?? '';

  getSemanticSimilarity() ignores its `apiKey` parameter for Gemini. It always
  reads the build-time ENV variable. The user-entered key from context is passed
  in as `apiKey` but only used for HuggingFace (line 145).

  This means:
  - QuestionGrader passes geminiApiKey from context to getSemanticSimilarity
  - That key is silently ignored for the Gemini path
  - If ENV var is not set, falls back to HF/keyword fallback with zero notice to user

  The GradingView / ocr.ts path correctly uses the context key. The similarity.ts
  path does not. Two identical questions graded by different paths will use
  different keys. This is a silent inconsistency.

  GradingView.tsx was rewritten to use the batch segmentation pipeline.
  QuestionGrader still exists and is presumably reachable from HistoryView
  (UpdateModal), but its grading logic uses the OLD per-question flow
  (extractAndGrade + calculateMarks threshold-based). HistoryView.tsx uses
  calculateMarksByMode correctly. QuestionGrader uses calculateMarks (threshold).
  Same codebase, two scoring systems, different results for the same input.

[HIGH] Model name hardcoded in 8 separate places
  'gemini-3.1-flash-lite-preview' appears in:
    src/services/ocr.ts (3 times: lines 23, 138, 296, 382)

SECTION 6 — BAD PATTERNS
--------------------------------------------------------------------------------

[HIGH] No React Error Boundary anywhere
  src/App.tsx renders everything without a single ErrorBoundary wrapper.
  If any component throws (corrupted localStorage, null pointer, API parse error),
  the entire app goes white. The user loses their current session and has no
  idea what happened. A single top-level ErrorBoundary would show a useful
  message and let them recover.

[HIGH] No AbortController on API calls
  segmentAndGradeAll() and gradeExtractedText() in ocr.ts make long-running
  fetch calls with no cancellation support. If the user navigates away mid-evaluation
  (switches tabs in the app), the fetch completes and calls setBatchResults on
  an unmounted component. React 18 handles this gracefully in most cases, but
  the wasted API quota and dangling async work is wasteful and can cause subtle
  state bugs. Add AbortController.

[MEDIUM] ExamSetup.tsx dispatches SET_CHECKING_MODE redundantly on step change
  Line 469: dispatch({ type: 'SET_CHECKING_MODE', payload: checkingMode });
  This fires when stepping between setup steps and dispatches the CURRENT value
  of checkingMode back to itself. It changes nothing and causes a needless
  re-render of all context consumers.

[MEDIUM] keywordOverlapScore returns 1.0 for two empty strings
  similarity.ts line 27:
    if (a.size === 0 && b.size === 0) return 1;
  If both extracted text and expected answer are empty (blank answer, blank
  expected), the function reports perfect similarity. This feeds into scoring.
  A blank answer should be 0, full stop.

[MEDIUM] HF API empty array edge case
  similarity.ts line 114:
    if (Array.isArray(data) && typeof (data as unknown[])[0] === 'number') return (data as number[])[0];
  If the HF API returns an empty array, `data[0]` is `undefined`, typeof is
  'undefined', the check fails, and the function throws 'Unexpected HF response
  format'. This is a recoverable error being treated as a hard failure.

[LOW] ExamSetup.tsx appears twice in the CheckingModeSelector rendering
  Lines 640 and 922 both render <CheckingModeSelector>. Verify these are in
  genuinely separate UI paths and not duplicated by accident.

SECTION 8 — TYPE SYSTEM ABUSE
--------------------------------------------------------------------------------

[MEDIUM] Dangerous assertion on FileReader result
  ocr.ts line 9-11:
    const result = reader.result as string;
    resolve(result.split(',')[1]);
  readAsDataURL always produces a string with the format "data:mime;base64,data".
  But if somehow `result` is null or doesn't contain a comma, `split(',')[1]`
  returns `undefined` and the base64 payload is undefined. The API call will
  fail with a cryptic error. Add a guard.

[MEDIUM] Regex JSON extraction is wrong for nested objects
  ocr.ts line 169: raw.match(/\{[\s\S]*\}/)
  ocr.ts line 318: raw.match(/\[[\s\S]*\]/)
  These use greedy matching. If the Gemini response contains text before the
  JSON that includes a `{`, the match starts too early. If the model adds any
  text after the closing `}`, the match is too long. The `[\s\S]*` is maximally
  greedy and will match from the FIRST `{` to the LAST `}` in the string.
  For a response like: 'Sure, here: {"a":1}. Hope that helps!'
  This works. But for: 'Error: {"details": "..."} and also {"result": 1}'
  You get the wrong object. Use a proper JSON extraction strategy.

[LOW] QuestionResult.status includes 'skipped' but QuestionResult type doesn't
  types/index.ts line 48: status: 'full' | 'partial' | 'zero' | 'skipped'
  Actually 'skipped' IS in the union. Fine. But statusColors in GradingView.tsx
  has an entry for 'skipped' that uses zinc colours. The ReportView table should
  also handle 'skipped' rows distinctly. Verify it does (it seems to handle it
  via the status check but worth confirming the visual output is sensible).
